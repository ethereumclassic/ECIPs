### Simple Summary

Establishes `MIN_MINER_TIP`, the minimum a block producer may be paid per unit of gas, at one gwei.

The value is enforced at two points every client already has — transaction-pool admission and block production — and is held as a client constant that an operator-supplied value does not replace. It applies to the legacy transactions Ethereum Classic carries today and requires no fee-market change to take effect. It is not a consensus rule, and no block becomes invalid under it.

### Abstract

This ECIP defines one value that all conforming Ethereum Classic clients enforce identically: `MIN_MINER_TIP`, one gwei, the minimum effective tip a transaction must offer the block producer.

**Ethereum Classic already enforces a tip floor. What it does not have is a single one.** The value is held today in per-node client configuration, at defaults that differ between its two client implementations and between the two points that enforce it, and any operator may replace it at startup or at runtime. This ECIP makes it network-authoritative: one value, shipped identically, not selectable per node.

**The floor is on what the producer is paid, not on what the sender pays**, which is what makes it independent of any fee market. Ethereum Classic has no base fee today — [EIP-1559](https://eips.ethereum.org/EIPS/eip-1559) is not active on it — and on a legacy transaction the producer receives the whole gas price, so the floor is a floor on the gas price itself. Where a base fee is in force the producer receives the remainder above it, and the floor applies to that. Nothing in this ECIP requires either regime.

It requires no consensus hard fork and no other specification. A coordinated client release is the whole of its deployment, and a client that does not implement it does not fork from the canonical chain.

### Motivation

**A gas price beneath which a transaction is not worth producing is a property Ethereum Classic operates by, and it is not a property of the network.** It is a value each client happens to ship, at a default it chose, which any operator may replace — and the two clients serving the network ship four such values between them, no two alike, one of which is zero.

| Client | Setting | Default | Enforced at |
| --- | --- | ---: | --- |
| core-geth | `PriceLimit` | **1 wei** | transaction-pool admission |
| core-geth | `miner.GasPrice` | **1 gwei** | block production |
| Besu | `DEFAULT_MIN_TRANSACTION_GAS_PRICE` | **1,000 wei** | both |
| Besu | `DEFAULT_MIN_PRIORITY_FEE_PER_GAS` | **zero** | both |

**Besu's priority-fee default is the one this ECIP most directly replaces.** A client whose shipped minimum priority fee is zero imposes no tip floor at all, and the thousand-wei minimum gas price beside it is six orders of magnitude below one gwei. The two implementations do not merely differ in degree; one of them ships the absence of the control.

**Within core-geth the two defaults differ from each other, so a transaction can be admitted at a price at which no block will carry it.** The pool accepts a tip of one wei and the block producer will not include one below a gwei. That gap is a user-facing failure rather than an accounting curiosity, and it is a present failure rather than one that waits on a fee-market change: Ethereum orders each account's transactions by a strictly continuous nonce, and core-geth's legacy pool promotes a queued transaction only when it fills the nonce gap. A transaction admitted at one wei and never mined therefore blocks every later transaction from the same sender, today, with no base fee anywhere in the picture.

**Neither value requires a restart to change, which is stronger than a startup flag.** A single remote-procedure call, `miner_setGasPrice`, resets both the pool floor and the production floor on a running core-geth node; Besu exposes `miner_setMinGasPrice` and `miner_setMinPriorityFee` for the same purpose. The `miner` namespace is absent from the HTTP and WebSocket defaults, but the IPC endpoint registers every namespace without a module filter, so the call is available to the node's own operator by default.

Below-floor traffic is also cheap traffic. A block producer accepting it imposes the cost on every other node, which must accept, validate and store the result.

### Specification

#### Constants

```
MIN_MINER_TIP = 1,000,000,000 wei = 1 gwei
```

#### Effective Tip

**The effective tip is the amount per unit of gas the block producer receives.** That definition holds whether or not a base fee is in force, and the arithmetic follows from which:

| Fee regime | Transaction form | Effective tip |
| --- | --- | --- |
| No base fee in force | any | `gasPrice` |
| A base fee in force | a single gas price | `max(0, gasPrice − baseFee)` |
| A base fee in force | a fee cap and a priority fee cap | `min(maxPriorityFeePerGas, maxFeePerGas − baseFee)` |

Where a base fee is in force, `baseFee` is that of the block the transaction is evaluated against: the next block at pool admission, the block being produced at block production. Introducing or removing a base fee changes which row applies and nothing else.

The set of valid transaction types is whatever the chain's fork configuration admits at the block being evaluated, and is not enumerated here. Each type takes whichever row matches the fee regime and its own fee fields, and no type is exempt, including any type a later upgrade adds.

#### Rejection Condition

A transaction MUST be rejected where:

```
effectiveTip < MIN_MINER_TIP
```

For a transaction carrying a single gas price this is `gasPrice < baseFee + MIN_MINER_TIP` where a base fee is in force, and `gasPrice < MIN_MINER_TIP` where none is.

#### Enforcement Points

Implementations MUST apply the check at **both** of the following, and neither discharges the other:

1. **Transaction-pool admission**, on receipt by remote procedure call or peer-to-peer gossip. Rejecting here is what protects a sender from a queue its own transaction has blocked.
2. **Block production**, on selecting transactions for inclusion, evaluated against the block being produced. Where a base fee is in force, a transaction admitted while its effective tip cleared the floor MUST NOT be included once a rising base fee has carried that tip below it.

An implementation checking only at admission still produces blocks carrying below-floor transactions, which every conforming node must then accept, validate and store.

#### Per-Network Configuration

| Network | chainId | `MIN_MINER_TIP` |
| --- | ---: | ---: |
| ETC Mainnet | 61 | 1,000,000,000 wei (1 gwei) |
| Mordor Testnet | 63 | 1,000,000,000 wei (1 gwei) |

**Clients MUST ship these values and MUST NOT let an operator configure a lower one, at startup or at runtime.** A remote-procedure call that sets a minimum tip MUST NOT bring either enforcement point below `MIN_MINER_TIP`, and an implementation that discards a startup flag while honoring such a call does not conform. An operator MAY configure a higher threshold for its own node; that is a local pricing decision which neither weakens nor represents the network value. Networks other than the two above are unaffected.

### Rationale

**A minimum miner tip is not a novelty — every client surveyed ships one.** What none of them does is make it binding on the party validating a block. The floor is everywhere enforced by the party choosing what to include, and it appears in no state-transition precondition, no block validator, and no transaction-validity rule. Six implementations across five languages, and no two agree on the value:

| Implementation | Setting | Shipped default | Enforced at |
| --- | --- | ---: | --- |
| core-geth, Go | `PriceLimit`; `miner.GasPrice` | 1 wei; 1 gwei | pool; production |
| Besu, Java | minimum transaction gas price; minimum priority fee | 1,000 wei; **zero** | both |
| Nethermind, C# | `MinGasPrice`, *"the minimum gas premium ... for transactions accepted by the block producer"* | 1 wei | production |
| reth, Rust | `--txpool.minimum-priority-fee` | **unset** | pool |
| Bitcoin Core, C++ | `DEFAULT_MIN_RELAY_TX_FEE`; `DEFAULT_BLOCK_MIN_TX_FEE` | 100; 1 | relay; production |
| Monero, C++ | `Blockchain::check_fee`, derived per block | dynamic | relay |

**Bitcoin is the oldest instance and the closest structural match.** It places the floor at exactly the two points §"Enforcement Points" names — relay admission and block assembly — as node policy rather than as a consensus rule, and it ships the two at different values, the same divergence this ECIP closes in core-geth. Bitcoin has no base fee at all, which shows the placement is not an artifact of EIP-1559.

**Monero is the case that most looks like a counterexample and is not.** Its minimum fee is no constant: `Blockchain::check_fee` derives it from the block reward and the median block weight, and rejects a transaction paying less than that minus a two-percent buffer. It is a method on the blockchain object, computed from consensus-relevant state, and it is still not a validity rule — its single call site in the transaction pool short-circuits on `kept_by_block`, so a transaction arriving inside a block skips the check entirely. A chain with a dynamic, consensus-derived minimum fee still declines to bind a validator with it.

**There is a structural reason the pattern is so uniform.** A base fee is a header field, recomputed and checked by every validating node; a tip is summarized in no header field, so a consensus-binding tip floor would require a new transaction-validity rule rather than a stricter reading of an existing one. There is also a reason not to want one. A producer that under-collects a base fee takes value that would have reached the base-fee destination, so every other node must be able to reject its block; a producer that under-collects the tip forgoes its own income, and the network's exposure is the externality of the extra data every node stores. Consensus exists to stop the first case. A validity rule for the second would make every historical block's validity depend on a pricing parameter the network may later want to change.

**What the instances differ in is where the value is held**, and there are four placements:

| Where the value is held | What can change it | In production at |
| --- | --- | --- |
| A client default, replaceable by a startup flag | any operator, per node | Ethereum Classic today |
| A client default, additionally settable at runtime by remote procedure call | any operator, without a restart | Ethereum Classic today |
| An on-chain contract read by the block producer | whoever controls that contract | Celo, whose `GasPriceMinimum` floor is set `onlyOwner` |
| **A client constant, with an operator-supplied value discarded at startup** | **a coordinated client release** | **Polygon PoS and Ronin** |

The first two rows are where Ethereum Classic sits, and they are the same row twice over — a per-node value, differing only in whether changing it costs a restart. The third moves the decision on-chain rather than removing it, so the question becomes who owns the contract. Ethereum Classic has no party outside consensus to whom this value could be entrusted, so it takes the last placement: a client constant, changed by the same instrument that installed it.

**Polygon Improvement Proposal 35 is the worked precedent, and it is exact.** It states that *"a minimum fee for transaction gas price is required in both the p2p and execution layers of the network"* and fixes the transaction-pool price limit and the block-production floor at 25 gwei, and on placement it is explicit: *"when a new backend is initialized at startup in the client, some utility functions will check for such values, and enforce them to be `25gwei`."* That is this ECIP's design already in production — the same two enforcement points, the same client-held placement, the same discarding of an operator-supplied value, and the same absence of any block-validity rule. It is implemented by more than one client: Erigon carries the pool floor as a constant and discards a differing operator value at startup with a sanitizing warning. Ronin enforces a tip floor at the same placement from its Venoki upgrade, on a network that floors both halves of the gas price.

**One gwei is one unit of the denomination in which gas prices are expressed**, rather than an arbitrary count of wei. Wallet interfaces quote, display and accept gas prices in that unit, so a floor of one whole gwei sits at the granularity at which users and tooling actually reason about price, and a floor below it does not. It is the magnitude the wider fee-market literature already uses for its own constants: EIP-1559 sets `INITIAL_BASE_FEE` at exactly one gwei. What this ECIP changes is not the number but that there is one.

**It is set before the subsidy declines, not after.** [ECIP-1017](https://ecips.ethereumclassic.org/ECIPs/ecip-1017)'s emission schedule falls on a fixed timetable, and fee revenue becomes the security budget as it does. A floor established while block subsidies still dominate miner income changes little for anyone; the same floor established once they do not is a change to miner economics under pressure.

**The cost to a legitimate user is negligible, and the same floor is real friction at volume.** A standard transfer consumes 21,000 gas intrinsically, so a one-gwei floor puts the minimum tip on one at 0.000021 ETC — which is what a sender already pays by the prevailing convention, and about two billion times the one wei a pool may currently admit. The floor therefore costs nothing to traffic priced by convention and prices only traffic deliberately below it. That asymmetry is the point: it is not a revenue measure, and it changes almost no sender's bill.

### Backwards Compatibility

**No block valid before this ECIP is invalid after it, and this ECIP does not change block validity.**

`MIN_MINER_TIP` governs which transactions a node admits and which a producer includes. A block carrying a below-floor transaction remains valid and MUST be accepted. A client that does not implement this ECIP therefore does not fork from the canonical chain; it admits transactions others reject.

Senders whose effective tip falls below the floor are affected from the release that ships it. Such a transaction is rejected at submission rather than accepted and left unmineable, so the failure is immediate and visible to the sender.

### Test Cases

Conformance vectors for §Specification. Each MUST fail an implementation that does not satisfy the requirement it exercises, and because `MIN_MINER_TIP` is per-network chain configuration, each MUST be run against both the ETC Mainnet (chainId 61) and Mordor Testnet (chainId 63) configurations.

| Case | Expected |
| --- | --- |
| Zero tip | rejected at pool admission. MUST be exercised in both fee regimes |
| Below floor | `effectiveTip < MIN_MINER_TIP` rejected at pool admission |
| Exact floor | `effectiveTip = MIN_MINER_TIP` admitted, and included when a block is produced |
| Single gas price, no base fee | `gasPrice < MIN_MINER_TIP` rejected; `gasPrice = MIN_MINER_TIP` admitted. **A suite run only against a base-fee configuration does not discharge this row** |
| Single gas price, base fee in force | `gasPrice < baseFee + MIN_MINER_TIP` rejected; `gasPrice = baseFee + MIN_MINER_TIP` admitted |
| Every valid transaction type | the floor applies uniformly across whatever set the chain's fork configuration admits, each type in whichever fee form it carries. **Vectors MUST be derived from that live set rather than from a fixed enumeration**, and a suite covering one fee form does not discharge this row |
| Enforcement at block production | a below-floor transaction reaching the pool by any route that bypasses admission MUST NOT appear in a produced block. **A vector exercising admission alone does not discharge this row** |
| Nonce-queue protection | after a below-floor transaction is rejected, a valid transaction at the same nonce from the same sender is admitted |
| Operator cannot lower the floor at startup | with a pool price-limit or block-production gas-price flag **set** below `MIN_MINER_TIP`, both points still enforce `MIN_MINER_TIP`. **A vector run without such a flag set cannot distinguish a network-authoritative value from a default** |
| Operator cannot lower the floor at runtime | with the node running, a remote-procedure call setting a minimum tip below `MIN_MINER_TIP` leaves both points at `MIN_MINER_TIP`. **An implementation that discards the startup flag but honors this call passes the preceding row and fails this one** |
| Operator threshold above the floor | a node configured higher rejects between the two values, and MUST NOT accept below `MIN_MINER_TIP` |
| Below-floor transaction in a received block | **valid.** MUST be accepted, validated and stored |
| Base fee rising after admission — base-fee regime only | a transaction whose effective tip falls below the floor as `baseFee` rises MUST NOT be included in a produced block. Not applicable where no base fee is in force |
| Tip cap distinguished from effective tip — base-fee regime only | a transaction whose priority-fee cap is at or above `MIN_MINER_TIP` but whose fee cap leaves less than that above the base fee MUST be rejected. An implementation comparing the cap rather than the effective tip passes every other row and fails this one |

### Security Considerations

**Enforcement is defense in depth rather than a guarantee, and its blast radius differs by role.** A non-conforming validating node does not threaten chain validity: it weakens its own spam resistance and may expose its own users to blocked nonce queues. A non-conforming block producer is a network-wide externality, because below-floor transactions it includes land in canonical blocks that every conforming node must accept, validate and store, and the quantity that fits in one block rises with whatever gas limit the network converges on.

**Against a determined producer, the only floor that binds is one consensus enforces.** This ECIP's floor is a conformant-network figure rather than a protocol guarantee. That is the honest bound on the anti-spam argument, and it is why the value requires cross-client adoption rather than treating it as a local preference. §Rationale states why a consensus rule is not the remedy.

### Implementation

`MIN_MINER_TIP` is distributed as chain configuration with client software rather than as a consensus rule, so a coordinated client release is the unit of deployment, and this ECIP schedules no activation block of its own.

**Enforcement does not wait on any other specification.** §"Effective Tip" is stated for both fee regimes, so a release may ship the floor whenever client implementers agree to, before or after a base fee exists on the network. Where a network later introduces one, the row that applies changes and the floor does not.

**Cross-client agreement is evidence that this specification is unambiguous only where the implementations do not share a codebase.** Before this ECIP advances to `Final`, the vectors above MUST be executed on at least two implementations whose transaction-pool and block-production code derive from unrelated upstreams, and both the vectors and their results MUST be published as data a third party can re-execute.
